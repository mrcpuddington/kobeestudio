## Before a testing release

1. Review the complete app diff, commit the intended changes and run CI against
   that exact revision. Retain the full test log and artifact.
2. Review the blog and GitHub notes. Confirm the version and testing channel.
   Keep the blog draft until the corresponding delivery is verified. Set its
   publication date to the actual publication date.
3. Run the Publish workflow with the tested source commit, `channel: testing`,
   `release_tag: v1.5.20-beta.1`, and an explicit release title. The metadata
   template is now testing; no stable release is implied.
4. Verify the pre-release asset and the testing PCM catalog. Exercise an update
   from the currently installed release and reopen existing artwork.

## Before the official GitLab update

The ZIP's public download must already exist. A local checksum alone does not
meet this requirement. Use the actual published ZIP, not a subsequent local
rebuild. Regenerate with fresh upstream metadata and `--verify-download`.

For a stable update, complete Windows/Linux visual acceptance, fabrication-view
acceptance and the remaining crash-environment checks; choose the stable source,
status and tag; publish and verify its artifact first. Refresh the notes to
reflect the final evidence. Avoid putting a testing 1.5.20 entry in the official
catalog before deciding its final artifact, because existing version checksums
cannot be changed later.

In a fresh checkout of your existing GitLab fork of the metadata repository:

The established fork is [mrcpuddington/metadata](https://gitlab.com/mrcpuddington/metadata).
The original submission was [merge request !640](https://gitlab.com/kicad/addons/metadata/-/merge_requests/640),
which is merged. Reuse that fork with a new release branch.

1. Update from `kicad/addons/metadata` main and create a release branch.
2. Copy only the generated
   `packages/com.github.mrcpuddington.kobeestudio/metadata.json`. Keep the existing
   icon unless an intentional replacement is reviewed. Confirm older versions'
   URLs, sizes and checksums are unchanged.
   Alternatively, run `git apply --check /path/to/official-submission/metadata.patch`
   and then `git apply` with the same patch after refreshing upstream.
3. Install the repository's `ci/requirements.txt` in a disposable environment.
   Run `ci/validate-package.py` with the new and old metadata and current v1/v2
   schemas, following its README and CI. It must download and validate the real
   public artifact. Local archive-backed validation is useful preparation but
   does not replace that check.
4. Push the branch to the existing fork and inspect GitLab CI. Use its temporary
   repository in KiCad PCM to test installation and upgrading.
5. Submit the merge request to **kicad/addons/metadata**, using the generated MR
   description and checking boxes only for evidence actually obtained.
6. After merge, verify the official catalog lists the version, then install from
   the default repository. Its scheduled catalog refresh may take up to a day.
   Publish the blog only after its installation wording matches real delivery.
